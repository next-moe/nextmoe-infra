资料库里最难收拾的不是错别字，而是**重复条目**：同一部作品建了两次、同一个人分成两个人物、同一个厂商出现三份。重复会让评分、收藏、关联、制作人员全都被拆散。这一篇讲怎样避免制造重复，以及发现重复时怎么处理。

## 新建之前先搜索 {#search-first}

新建任何条目前，先在编辑台顶部的搜索框，或对应列表页（[/works](/works)、[/characters](/characters)、[/companies](/companies)……）里搜一遍：

- 用原文名搜，也用中文名、罗马字、常见简称各搜一遍；
- 作品记得搜系列里的其他作品——你要找的可能是另一个版本；
- 人物和署名名搜所有已知的笔名。

> [!IMPORTANT]
> 搜不到不等于不存在。资料源导入的条目可能用的是另一种写法（例如日文汉字与简体字、全角与半角）。至少换两三种写法再搜。

## 新建的入口与规则 {#creating}

顶栏的「+」菜单和各列表页的「新建」按钮都能进入新建页面（`/new/<类型>`）。新建本身也是一条提案，计入提案额度，按[角色、权限与配额](/guidelines/roles-and-quotas)里的规则审核。

| 类型                           | 说明                                                                                                                                                                                         |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 作品                           | 走「认领」流程（`/new/work`）：填显示名、原语言、原文标题、资料站链接、发售日期。**如果填写的资料站链接已经对应到某部作品，会直接认领那部作品而不是新建。**目前只能新建 Galgame 类型的作品。 |
| 发行                           | 必须挂在一部已存在的作品下，从作品的「发行」分区或作品详情页进入                                                                                                                             |
| 角色、厂商、系列、引擎、署名名 | 任何人都可以新建                                                                                                                                                                             |
| 人物                           | 从一个**还没有归属任何人物**的署名名建立（人物总是由署名名「长」出来的，见[署名名与人物](/guidelines/credit-names-and-persons)）                                                             |
| 标签、特质                     | 只有审核者可以新建                                                                                                                                                                           |

### 疑似重复提示 {#duplicate-suspects}

提交新建时，系统会把名称规范化（统一大小写、全角半角等）后和已有条目比对。如果有同名条目，会弹出「疑似重复」列表：

- **逐个点开看**：是不是同一个东西？
- 确实是同一个：取消新建，去编辑已有的条目。
- 确实不是（例如同名的两个不同角色）：确认后继续新建，并在修改说明里写清楚它和同名条目的区别。

作品的查重只和**同一媒介**的作品比较；认领已有作品时不触发查重。

## 什么算「同一个」 {#what-counts-as-same}

这是最容易判断错的地方。原则：**看它在现实中是不是同一个东西，而不是看名字像不像。**

| 情况                                  | 是否同一条目 | 应该怎么处理                                                                     |
| ------------------------------------- | ------------ | -------------------------------------------------------------------------------- |
| 同一部作品的普通版、限定版、下载版    | 同一部作品   | 一部作品，多个[发行](/guidelines/releases)                                       |
| VNDB 列在同一个条目下的移植版、重制版 | 同一部作品   | 一部作品，多个发行；已经分开建了就合并                                           |
| VNDB 单独收录的重制版、移植版         | 不同作品     | 分开建立，用[关联作品](/guidelines/relations-and-series)标记「重制」             |
| FanDisc、续作、外传                   | 不同作品     | 分开建立，用关联作品标记                                                         |
| 合集（收录多部作品）                  | 不同作品     | 合集单独一部，用「收录」关联到各作品                                             |
| 同一位画师用了两个笔名                | 同一个人物   | **一个人物、两个署名名**，不要建两个人物                                         |
| 两位不同的声优恰好同名                | 不同人物     | 分开建立，在备注里写区分信息                                                     |
| 同一角色出现在续作里                  | 视情况       | 续作里的那份角色条目用「实例归属」指向主条目（见[角色](/guidelines/characters)） |
| 厂商改名（公司没变）                  | 同一个厂商   | 一个厂商，旧名作为别名                                                           |
| 品牌从母公司独立                      | 不同厂商     | 分开建立，用厂商关系标记                                                         |

### 拿不准时以 VNDB 的划分为准 {#vndb-granularity}

作品的粒度跟随 VNDB：VNDB 把一个版本列为某个条目下的**发行**，它在这里就是同一部作品的发行；VNDB 为它单独建了条目，它才是另一部作品。资料库的自动导入按这个粒度把各资料源对到一起，跟着它走，导入才不会和人工编辑互相打架。

例如 1998 年的 Windows 重制版「脅迫 ～終わらない明日～」：Bangumi 和批评空间各有一个单独的条目，但 VNDB 把它列为 v4302「脅迫」的一个发行，所以它和「脅迫」是同一部作品，分开的两个条目应该合并。

> [!NOTE]
> Bangumi、批评空间常把同一部作品的不同版本分开收录，它们分开不能作为「不同作品」的依据。合并后，被并入方在这些网站的条目会保留为相关链接。

## 合并请求 {#merge-requests}

发现两个条目其实是同一个东西时，在其中一个条目的详情页点「合并」，会在**新标签页**打开合并工作台：

1. **选定两边**：左边是「被并入」，右边是「保留」，⇄ 可以交换方向（通常保留资料更完整、被引用更多的那个）。只选了一边时，下方会列出可能重复的条目，也可以直接搜索。
2. **三栏对照**：每个分区都按「被并入 · 保留 · 合并后」三栏排列，左栏导航上的数字是条目数，黄色数字是需要你留意的地方：
   - **基本信息**：显示名、原语言等，点一边的卡片选择保留哪个值；保留方空缺或人工填写的项不能选，卡片上会写明原因；
   - **标题、简介**：保留方已有标题的语言里，被并入方的标题改为别名；每种语言只留一份简介；
   - **发行**：被并入方的发行全部移过来，与保留方重复的（同一个 VNDB 发行，或平台和发售日相同）默认勾选「合并后隐藏」，鼠标移上去会标出它和哪一个重复；
   - **资料源对应**：保留方在同一个网站已有正式对应时，被并入方的对应会降为相关链接或待确认，旁边写着原因；
   - **关联数据、用户数据、认领与下游**：会移过来多少、合为一条多少。
3. **查看结果**：顶栏「查看结果」只列出合并会给保留方带来的变化。
4. **提交**：写理由（必填）——为什么认为它们是同一个，有哪些依据。系统会把在数据里找到的依据（例如「VNDB 只收录了某一边」「两边有平台、发售日相同的发行」）列出来，点一下就能加进理由。

提交后进入[请求审核](/review/requests)队列，由拥有合并审核权（`catalog.merge.review`，默认 moderator、admin、ren）的人决定。审核者打开的是同一个工作台，可以直接调整基本信息和要隐藏的发行再批准，修改会记在请求上。

可以发起合并请求的类型：作品、厂商、角色、人物、署名名。**不同媒介的两部作品不能合并**（例如游戏和它改编的动画），工作台会直接提示——它们本来就是不同的作品，应该用关联作品连接。

### 合并请求的流程 {#merge-lifecycle}

| 阶段             | 说明                                                                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 待审核           | 你可以在请求页面或 [/me/merge-requests](/me/merge-requests) 撤回                                                                                        |
| 已批准（冷静期） | 审核者批准后，要等待一段冷静期（默认 48 小时，`catalog.merge_cooling_off_hours`）才会执行。这段时间留给大家发现问题；如果你发现不该合并，立刻联系审核者 |
| 已合并           | 冷静期结束后由每小时运行的任务自动执行，或由审核者手动执行                                                                                              |
| 已撤销           | 审核者在撤销期内撤销了这次合并，被并入的条目以原编号恢复                                                                                                |
| 已驳回           | 审核者认为不该合并                                                                                                                                      |

请求页面顶部的时间线显示走到了哪一步、冷静期还剩多久。合并请求也有额度（默认普通用户 24 小时内 10 次，见[配额](/guidelines/roles-and-quotas#quotas)）。

### 合并之后会发生什么 {#after-merge}

- 被并入的条目变成**重定向**：旧链接、旧编号仍然能访问，会跳到保留的条目；下游站点通过重定向通知跟着跳转；
- 两边的资料、外链、关联、收藏、评分并到保留的条目上，保留方原有的资料优先；同一位用户在两边都有的评分和游玩状态保留较新的一条；
- 被并入条目上待审的提案会被自动拒绝（条目已经不存在了）；
- 隐藏记录、人工修改随之迁移；
- 合并前的状态会被完整记录下来，用于撤销。

### 撤销合并 {#undo-merge}

执行后的一段时间内（默认 30 天，`catalog.merge_undo_window_days`），审核者可以在请求页面点「撤销合并」：

- 被并入的条目以**原编号**重新上线，下游站点会收到「重定向已撤销」的通知；
- 合并时移过去的发行、标题、资料源对应、评分等移回；合并时隐藏的重复发行重新显示；
- 保留方被替换掉的显示名等还原——除非合并后又有人改过。

> [!CAUTION]
> 撤销不是时间倒流：合并时两边合为一条的数据（例如同一位用户在两边的评分）、合并后新导入或新编辑到保留方的内容，都留在保留方。拿不准的合并请求，宁可在理由里写明疑点让审核者判断，也不要「先合了再说」。

## 删除条目 {#deleting}

删除是最后的手段。资料写错了应该**修改**，两个条目其实是同一个东西应该**合并**；只有条目本身就不该存在时才删除。

| 情况                                                   | 应该怎么做                     |
| ------------------------------------------------------ | ------------------------------ |
| 标题、发售日、制作人员等资料写错了                     | 编辑资料                       |
| 同一部作品建了两次，或把一个版本建成了单独的作品       | 发起合并请求                   |
| 查不到任何发售、发布或官方信息，是编造或误建的条目     | 删除，原因选「不存在的作品」   |
| 作品存在，但不属于收录范围（例如是动画，不是视觉小说） | 删除，原因选「不属于收录范围」 |
| 广告、恶作剧、乱码，或明显用于测试的条目               | 删除，原因选「恶意或测试条目」 |

### 怎样发起删除 {#deletion-requests}

在作品详情页右上角的「⋯」菜单里选「申请删除」。弹窗会列出删除会影响什么：作品持有的资料源对应、发行、用户数据、待审提案、认领它的站点。选好原因，在说明里写出你查过哪些地方，审核者会照着核实。目前只能删除作品。

删除请求由拥有删除审核权（`catalog.delete.review`，默认 moderator、admin、ren）的人处理，流程和合并请求一样：

| 阶段             | 说明                                                                   |
| ---------------- | ---------------------------------------------------------------------- |
| 待审核           | 你可以在 [/me/deletion-requests](/me/deletion-requests) 撤回           |
| 已批准（冷静期） | 默认 48 小时（`catalog.deletion_cooling_off_hours`），留给大家发现问题 |
| 已删除           | 冷静期结束后由每小时运行的任务执行，或由审核者手动执行                 |
| 已恢复           | 审核者把它恢复了                                                       |

同一部作品同时只能有一个删除请求。删除请求也有额度（默认普通用户每个统计窗口 5 次）。

### 删除之后会发生什么 {#after-deletion}

- 作品从列表、搜索和详情页消失；各站点的作品页显示「已删除」和原因。
- 它和 VNDB、Bangumi 等资料源的对应关系**保留下来**，导入任务不会再把它建出来。
- 用户的评分、收藏、游玩时长与游玩状态**保留但不显示**。
- 作品上待审的编辑提案会被驳回。
- 审核者可以随时**恢复**：作品以原来的 ID 回来，用户数据一并回来。

> [!WARNING]
> 不要用删除处理重复条目。删除不会把评分、收藏转到另一个条目上，只会把它们藏起来；重复条目要用合并。

## 常见错误 {#common-mistakes}

| ❌ 做法                      | 后果                               | ✅ 应该                                          |
| ---------------------------- | ---------------------------------- | ------------------------------------------------ |
| 没搜索就新建作品             | 制造重复，评分收藏被拆散           | 多种写法搜索后再建                               |
| 把限定版建成单独的作品       | 重复作品                           | 建成同一作品下的发行                             |
| 把同一个人的笔名建成两个人物 | 作品履历被拆散                     | 一个人物下挂多个署名名                           |
| 对游戏和它的动画发起合并     | 被拒绝                             | 用关联作品「改编」连接                           |
| 合并理由只写「重复」         | 审核者无法核实                     | 写出依据：同一个外部条目、同一张包装、官方说明…… |
| 疑似重复提示直接点继续       | 制造重复                           | 逐个点开核对                                     |
| 用删除处理重复条目           | 评分收藏被隐藏，没有并到另一个条目 | 发起合并请求                                     |
