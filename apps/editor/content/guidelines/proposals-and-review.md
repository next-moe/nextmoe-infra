资料库里的每一次变化都有记录，可以追溯、对比、撤销。理解「提案」和「修订」这两个词，就理解了整个编辑流程。

## 提案与修订 {#proposal-and-revision}

- **提案**：你提交的一组修改，针对**一个条目**。它记录了你改了哪些字段、改成什么、修改说明，以及你开始编辑时条目处于哪个版本（称为「基准版本」）。
- **修订**：提案生效后，条目的版本号加一，留下一条修订记录：这一版改了哪些字段、改后完整的内容、由谁提出、由谁合并。修订历史在 `/history/<类型>/<编号>` 查看，也可以从编辑工作区右上角「⋯ → 修订历史」进入。

一条条目第一次被人工编辑时，系统还会另存一份编辑前的原始状态，历史页显示为「导入原始状态」，它是回滚的最后一道底。

## 提案的生命周期 {#lifecycle}

| 状态   | 含义                               |
| ------ | ---------------------------------- |
| 待审核 | 已提交，等待有审核权的人处理       |
| 已合并 | 修改已写入资料库，产生了一条修订   |
| 已拒绝 | 审核者拒绝了整条提案，并写了理由   |
| 已撤回 | 提案人（或审核者）在处理前撤回了它 |

**直接生效**是一种特殊的合并：如果你本人就有资格合并这次修改（审核者、作品主人、编辑者在免审额度内改作品或发行，见[角色、权限与配额](/guidelines/roles-and-quotas#per-entity-rules)），提交的同时就会合并，不进入待审队列。编辑台在提交前会告诉你是「提交后直接生效」还是「提交后进入审核」。

## 提交一次修改 {#submitting}

1. 在编辑工作区里修改。改过的字段左侧出现蓝色竖线，左栏对应分区显示修改数。
2. 点顶栏「查看更改」核对每一处前后差异；不想要的可以在这里单独撤销。
3. 点「提交」（或按 Ctrl / ⌘ + S），写**修改说明**：改了什么、依据是什么（官网链接、包装扫描、游戏内制作人员表……）。
4. 提交时系统会检查你编辑期间这些字段有没有被别人改过；如果有，会列出字段并提醒你提交会覆盖它们，请先确认。

一次提交可以同时包含作品和多个关联条目（例如在「角色」分区里顺手改了两个角色）——每个条目各生成一条提案，共用同一段修改说明，各自独立审核。提交完成的对话框里列出每条提案的状态和链接。

### 修改说明怎么写 {#writing-notes}

| ✅ 好的说明                                                            | ❌ 不好的说明 |
| ---------------------------------------------------------------------- | ------------- |
| 「按官网 STAFF 页补全原画与剧本：https://…」                           | 「完善资料」  |
| 「中文正式名以官方微博 2024-05 公告为准，旧名改为别名」                | 「改名」      |
| 「隐藏 Bangumi 导入的『同居』标签：剧情中没有同居情节，VNDB 也未标注」 | （留空）      |

审核者看不到你的屏幕，也不知道你查过什么。说明越具体，审核越快、越不容易被退回。

### 草稿 {#drafts}

编辑过程中，每个条目的修改会自动保存在**你这台设备的浏览器**里。下次打开同一个条目会提示「发现未提交的草稿」，可以恢复或丢弃；如果这期间条目被别人改过，会提醒你恢复后仔细核对。所有本机草稿在 [/me/drafts](/me/drafts) 列出。

> [!WARNING]
> 草稿只存在当前浏览器里，换设备、清除浏览器数据都会丢失，也不会被任何人看到。改到一半要离开，最好先提交。

## 审核者如何处理提案 {#reviewing}

审核在 [/review](/review)（审核工作台）进行，有审核权的人才能看到。打开一条提案后，每个字段单独显示「当前值 → 提议值」的对比，审核者对**每个字段**做出决定：

| 决定 | 快捷键 | 效果                           |
| ---- | ------ | ------------------------------ |
| 采纳 | `a`    | 按提议值写入                   |
| 修正 | `e`    | 审核者改成自己确认后的值再写入 |
| 拒绝 | `r`    | 这个字段不写入，其他字段照常   |

做完决定后点「合并」（`m`）：被拒绝的字段从提案里去掉、被修正的字段换成修正后的值，其余字段按提议写入——**一次合并只产生一条修订，要么全部写入，要么一个都不写**。如果所有字段都被拒绝，就应该直接「拒绝整条提案」（`d`），并写明理由，提案人会看到。

修正和拒绝都会留下记录：提案页能看到原始提议、谁修正了什么、最终写入的是什么。

### 冲突 {#conflicts}

提案提交后、合并前，条目可能已经被别的提案改过。如果被改过的恰好是这条提案也要改的字段，这个字段就**冲突**了，审核工作台会把它标成冲突字段，并注明「提案之后第 N 版也改过这个字段」。

为什么要拦下来：提案人写下提议值时，看到的是旧版本；直接按提议写入会把别人后来的修改悄悄覆盖掉，而这两个人都不知道。

冲突字段会同时列出三份值：**提案时**（提案人看到的版本）、**现在**（之后被改成的样子）和**提议**。审核者从四种处理方式里选一种：

| 处理方式     | 快捷键 | 效果                                                                           |
| ------------ | ------ | ------------------------------------------------------------------------------ |
| 自动合并     | `a`    | 把提案的改动套用到现在的值上，两边的修改都保留。只有两边改的不是同一处时才能用 |
| 采用提案的值 | `o`    | 用提议值覆盖之后的修改                                                         |
| 保留现在的值 | `c`    | 丢弃提案对这个字段的修改，其余字段照常处理                                     |
| 手动合并     | `e`    | 以合并结果为起点，审核者自己调整出最终值                                       |

什么时候能自动合并：

- **列表字段**（标题、标签、制作人员、外链……）按行比较：两条修改动的是不同的行，或者同一行里的不同项，就能自动合并；
- 两边把**同一行的同一项**改成了不同的值，或者是**单个值**的字段（发售日、显示名……），就不能自动合并，需要在后三种里选。

侧栏会汇总这条提案有几处冲突、几处可以自动合并，并提供「可自动合并的全部采用自动合并」一键处理。**所有冲突都处理完之前，「合并」按钮不可用。**如果在你审核期间条目又被改了，点合并时系统会重新加载并标出新冲突，什么都不会写入。

> [!IMPORTANT]
> 自动合并的结果仍然要看一眼。系统只保证两边的修改没有落在同一处，不保证合起来之后的内容是对的。例如两人各自加了同一个人的不同署名名，合并后会出现两条。

没有冲突的字段不受影响，可以照常采纳、修正或拒绝。

### 审核时看什么 {#review-checklist}

- 依据是否可靠（见[资料来源与可信度](/guidelines/sources)）；
- 是否把资料源的数据误删，而不是隐藏（见[资料源数据与人工编辑](/guidelines/upstream-data)）；
- 剧透等级、内容分级、图片分级是否如实；
- 是否混入了无关修改；
- 新建条目是否其实已经存在（重复）。

## 撤回与重新编辑 {#withdraw-and-reedit}

- 提案在被处理前，提案人可以在 [/me/proposals](/me/proposals) 撤回。
- 想在原提案的基础上改一改再提交：在提案页点「基于此提案重新编辑」，编辑台会打开条目并把原提案的修改载入，调整后重新提交（记得撤回旧的那条）。
- 提案被拒绝后不能修改，只能重新提交。

## 回滚 {#reverts}

有审核权的人可以在修订历史页回滚条目。回滚本身也是一条新修订，所以回滚也能再被回滚，什么都不会真正丢失。

| 方式             | 效果                                                 | 适用场景                     |
| ---------------- | ---------------------------------------------------- | ---------------------------- |
| 恢复到某一版     | 条目的**所有字段**回到那一版之后的内容               | 某次之后的一连串修改都不可信 |
| 撤销某一版       | **只把那一版改过的字段**放回它之前的值，其他字段不动 | 只想撤掉其中一次错误修改     |
| 回到导入原始状态 | 回到第一次人工编辑之前的样子                         | 人工修改整体有问题           |

「撤销某一版」时，如果之后又有修订改过同一个字段，系统会报冲突并列出字段，不会写入任何东西。审核者可以确认后强制执行（覆盖之后的修改），或改用「恢复到某一版」。

> [!CAUTION]
> 强制撤销会覆盖之后其他人的修改。执行前在历史页对比清楚，必要时只修正个别字段，而不是整体覆盖。

## 通知 {#notifications}

你的提案被合并或拒绝时，编辑台顶栏的通知会提示你；拒绝时附带审核者写的理由。[/me/proposals](/me/proposals) 列出你提交过的全部提案和状态，[/me/contributions](/me/contributions) 汇总你的贡献。

## 常见错误 {#common-mistakes}

| ❌ 做法                                  | 后果                       | ✅ 应该                                      |
| ---------------------------------------- | -------------------------- | -------------------------------------------- |
| 修改说明留空或只写「修正」               | 审核者无从判断，常被退回   | 写清依据与范围                               |
| 一次提交混入大量无关修改                 | 一处有问题拖累整条         | 按主题拆开提交                               |
| 提交后又开一条重复改同一字段             | 后合并的那条会和前一条冲突 | 撤回旧提案，基于它重新编辑                   |
| 冲突字段不看三方对比就选「采用提案的值」 | 别人后来的修改被覆盖       | 先试自动合并，不能自动合并时对照三份值再决定 |
| 发现错误就把条目恢复到很早的一版         | 冲掉中间所有人的有效修改   | 优先用「撤销某一版」只撤错误那次             |
